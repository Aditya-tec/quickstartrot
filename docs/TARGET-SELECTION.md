# How QuickstartRot chooses its targets

This file is the selection protocol for the tracked quickstarts, and the public record of every candidate that was looked at,
including the ones that were left out and why. It was written **before** any new target was chosen. The result tables at the end
are filled in as candidates are checked.

QuickstartRot publishes whether developer quickstarts work. A list chosen to find failures would make that claim worthless, so
the rule for choosing is stated first:

> **The goal is a representative sample, not a hunt for failures.** A target is chosen because it is a quickstart people really
> follow and one we can test fairly, never because we expect it to be broken. We do not look at whether a quickstart is likely
> to fail, and we do not drop a target because it passes. A target is excluded only for the reasons below, which are about whether
> it can be tested honestly, not about what the test would show.

## Criteria

A candidate is accepted only if all of these hold:

1. **Public docs.** The quickstart is a public page anyone can read, with no login wall.
2. **robots.txt allows crawling** of that page for the user agent `QuickstartRotBot`. A disallow, or a robots file that cannot be
   read, excludes it. Excluded targets are never fetched again.
3. **A code-first quickstart for Node.js or Python:** an install step and a short snippet that can be copied from the page. A page
   that is a product tour, a dashboard walkthrough or only prose does not count.
4. **Testable at L2 or L3 without a sign-up.** L2: it installs and the snippet's code imports or compiles. L3: the snippet also
   reaches the vendor's API, where an authentication error with a dummy key counts as a pass. A quickstart whose first step is
   "sign up and copy your key" is accepted only if L3 with a dummy key still proves something real (the client reaches the right
   endpoint). We never automate a sign-up, never solve a CAPTCHA and never use a real vendor key.
5. **No terms of service that forbid automated access.** We read the terms (or the repository's licence and contribution notes)
   where they exist. If they forbid automated access, we skip the target. If they are unclear, we note that and skip it.
6. **A product or project people actually adopt.** A vendor with real users, or an open-source project with real downloads. We do
   not pick abandoned or toy projects, and we do not pick a project for being obscure.

A candidate is also excluded, and the reason is recorded, when:

- the first step is an **interactive scaffolder** (a command that asks questions), because a fresh machine cannot answer it;
- there is **no install step** or nothing that runs (pure configuration pages);
- the quickstart needs **a running service, a browser or a mobile device** that the sandbox does not provide;
- the page is **not extractable** (the code is in images or in a canvas, or there is no stable container to crawl).

## Mix

The aim is 50 enabled targets:

- about **40% well-known libraries and frameworks** (web frameworks, validation, testing, HTTP clients, loggers, ORMs, CLI
  helpers), in Node.js and Python;
- about **60% funded devtool SDKs and API clients**: databases and serverless data, queues and background jobs, email and
  messaging, authentication, observability and analytics, vector stores and search, payments, AI and LLM clients and
  scaffolders. This includes long-tail vendors, not only the famous ones.

Both groups are sampled the same way. The mix is a target, not a quota that overrides the criteria: if fewer candidates qualify
in a group, the list is shorter and we say so.

## Process

For every candidate, in this order:

1. **Look at it once** and record it in the candidate table, with its docs URL, language and why it is in or out.
2. **Check robots.txt and the terms** before the page is fetched by the crawler for the first time.
3. **Write `targets/<slug>.yaml`.** The `owners` field is filled only from the vendor's own docs or repository, and left empty
   when there is any doubt. The page is fetched at most once per domain per cycle, as in production.
4. **Run it by hand:** `qsr run <slug>` in real Docker (crawl, compile, execute, classify). Read the logs.
5. **Decide `enabled`.** A target is `enabled: true` only if its result is **explainable**: a PASS, or a failure we can attribute
   to a specific cause (a bug in the docs, an API change, a dependency problem). A result we cannot explain, a flaky one, or one
   that looks like our harness's fault stays `enabled: false`, with the reason in `notes`.
6. **Write what we saw in `notes`:** the level reached, what the logs showed, and any quirk of the page (tabs, ESM and CommonJS
   variants, a scaffolder). A failure we can explain is recorded as a failure and is never "fixed" by editing the target to make
   it pass.

A target that fails for an explainable reason is kept enabled on purpose: a failing quickstart is a result, and hiding it would
bias the sample the other way. It is not published as broken: that needs two failures in valid cycles and a person's review.

## Calibration targets

Three targets exist to check that the pipeline works, not to say anything about a vendor: `chalk-node`, `loguru-python` and
`dotenv-python`. They have no API to reach, so a pass proves that installing and running work, not that anyone's endpoint is
wired up. Their notes say so. `hono-node` stays as a deliberate **"needs a person"** example: its quickstart begins with an
interactive scaffolder, so the correct plan is a single manual step. It shows what a manual stop looks like and is not counted
in the headline.

## Pages that print a rotating value (`extract.hashIgnore`)

The content hash of a page is the plan-cache key, so a value on the page that changes by itself (a demo key the site generates for each
visitor, a date, a nonce) makes the key change and costs one compile each time. The Ably quickstarts are the case found so far: they print
a demo API key `xVLyHw.<id>:*****` whose id rotates every few hours. `qsr calibration-report` now lists any page with 3 or more distinct
hashes in its window ("Content hash churn") so the next one is found by the report and not by hand.

A target can declare rules that are applied **only when its content hash is computed**:

```yaml
extract:
  root: main article
  hashIgnore:
    - pattern: '\b([A-Za-z0-9_-]{5,8})\.[A-Za-z0-9_-]{5,8}:(?=\*{3,})' # <prefix>.<id>: followed by a mask of 3 or more stars
      replaceWith: '$1.KEYID:'
```

- Each rule is a regular expression (applied globally to the text of every block) and its replacement; `$1` style references work. Up to 5
  rules; a pattern up to 200 characters, a replacement up to 100.
- The extraction that is stored and shown, and the plan, keep the **verbatim** text. Only the hash ignores the value. A plan cached under a
  hash is therefore run as it was compiled (with the key id it saw then), which for a demo key that L2 never contacts does not matter. If a
  rotating value ever mattered to what runs, this field is the wrong tool.
- Patterns are checked when the target loads: an invalid regular expression, a back-reference, or a quantified group that contains a
  quantifier or an alternation (`(a+)+`, `(a|aa)*`) is rejected, so a pattern cannot backtrack catastrophically over a page.
- A pattern must be narrow enough that it cannot hide a real change. The Ably rule needs the mask of stars, which a real key never has; a
  real-looking key with the same prefix is not normalized (tested).
- `qsr plans push` and `POST /admin/plans/import` apply the same rules to both the plan and the extraction before the grounding validator
  compares them, for these targets only, so a plan compiled before the key rotated is still accepted. The plan stored is the one sent.
- A target without `hashIgnore` hashes exactly as before. `packages/core/src/content-hash.test.ts` pins this on a gzipped fixture of 51
  live pages whose hashes were made by the function before the field existed; `committed-targets.test.ts` allows the field only on the two
  Ably targets.

## What a result means

The result of one local run is evidence for the decision above, nothing more. The numbers on the site come from the scheduled
runs, which are validated by the canaries and reviewed by a person before anything is called failing.

## Candidates and results

Looked at: **183** candidates. **51 enabled**, 16 written and run but disabled with a reason, 90 excluded before or after a probe, 26 passed the probe but were not run in P9a (the 50-target goal was met). Status as of 2026-10-19.

Mix of the 51 enabled: 20 libraries and frameworks, 28 vendor SDKs and API clients, 3 calibration targets. Without the calibration targets the sample is 42% libraries and 58% vendors (goal: 40 and 60). Levels: 5 at L3 (the vendor's API is reached), 46 at L2 (installed and built; many docs pages show only an install command, so those runs reach L1 and the public page says so). Most vendor quickstarts need an account to go beyond that, and the harness never signs up for one.
